# Backlog

Improvements agents noticed while building something else. One line each, with the task id that
spotted it. Nothing here is committed work — it is a list of candidates for the owner to promote
into `TASK_GRAPH.yaml` if worth doing.

Agents: add a line here rather than expanding your task's scope (AGENTIC_CONTEXT.md §1).

| C.1 | M1.2's acceptance covers spacing, backoff and the 403 hard stop but not payload validation. | C.3 | Alert dedup state is per-process and lost on restart, so a crash-looping component alerts on every start. A journal-backed `last_alerted_at` table would make suppression survive restarts — worth doing once A9's journal exists. |
| C.3 | Nothing yet turns a FAILED streak, red quality or a recon break into an `Alerter.send` call; C.3 built the channel only. M1.2, D7 and X1's recon each own their own trigger, and no task owns the severity/dedup-key convention across them. |
| C.2 | `nse_holidays.yaml` coverage ends 2026-12-31 and `expected_sessions` refuses dates past it by design, so the daily job will hard-fail in Jan 2027 unless someone appends the new year. Nothing schedules that refresh from the NSE holiday master (fetchable, one request) — a December reminder or an auto-refresh task would close it. |
| C.2 | For 2016-2025 the calendar's weekday closures are verified but weekend-falling holidays are not enumerated (a non-session weekend is indistinguishable from a weekend holiday). Harmless for gap reporting; it would matter to anything that wants the exchange's declared holiday list verbatim. |
| M0.4 | Nothing applies migrations on container start: a fresh `make up` leaves the app talking to an unmigrated DB until someone runs `make migrate`. An entrypoint step (or a `/health` degradation when `schema_migrations` is behind the files on disk) would make the gap visible instead of latent — belongs with whatever owns the app entrypoint. |
| M4.4 | The 2017-2024 schedules in `execution/costs/rates.yaml` are reconstructed from secondary sources (only the current one is read off the published rate card). A single real contract note from 2018 and one from 2022 would let them be verified to the paisa; the residual uncertainty is paise per ₹50k trade, all of it in the exchange/SEBI/GST block. |
| M4.4 | Pre-2020 state-wise stamp duty is encoded for KA and MH only, and the states that capped duty per contract note (Telangana, Haryana) are not modelled at all — an unlisted state raises. Only matters if a pre-July-2020 backtest is run for an account registered elsewhere. |
| M4.4 | The rate card starts at 2017-07-01 (GST rollout), so a backtest reaching into the service-tax era raises rather than pricing. The 10-year backfill horizon crosses that boundary in mid-2016; a service-tax schedule (14% + SBC + KKC) would close it. |
| M0.7 | Nothing prunes `ops/backups/`, and nothing schedules `make backup` — it is hand-run until M0.6's scheduler owns the daily pipeline. Retention becomes a real decision the moment an object-storage target exists. |
| M4.4 | Only delivery equity has a rate card. Intraday, F&O, currency and commodity are deliberately absent; when a task needs them they belong in `rates.yaml` and `execution/costs/model.py`, never in a second module (invariant #4). |
| M1.2 | The fetcher deliberately does not validate payload shape (the C.1 row above): a soft-404 answering 200 + HTML is checksummed into L0 like any other body, which is correct for L0 — it stores what the source served — but means FETCHED is not the same as usable. The check belongs in M1.3's FETCHED→VALIDATED transition and in each parser's era check; no task owns it today. |
| M0.6 | Nothing runs the scheduler: `ops/docker-compose.yml` has postgres + the status API only, so `python -m dataplatform.scheduler run` is hand-started. The service belongs beside `app` (same image, different command) — natural to add with M1.11, when the EOD job stops being a no-op. |
| M0.6 | A job's `timeout` is a budget the runner reports on, not a kill (CPython cannot safely kill a thread mid-transaction). A genuinely hung job therefore holds its advisory lock for as long as it hangs and never runs again. A watchdog that alerts on a `job_run` row left `RUNNING` past its budget (C.3's channel exists) would make that visible; today only `/health` going stale would. |
| M0.6 | `job_run` grows one row per attempt forever and nothing prunes it. Harmless at one daily job; worth a retention decision alongside `ops/backups/` before the intraday announcement polls (§8.1) land. |
| M2.1 | `corporate_actions.action_type`'s CHECK in `0001_init.sql` predates the M2.1 taxonomy: it allows `CONSOLIDATION`/`OTHER` and rejects `SCHEME_OF_ARRANGEMENT`, `DVR_CONVERSION`, `NAME_CHANGE`, `BUYBACK` and `DELISTING`, so five of the twelve normalized types cannot be stored today. M2.2 is the first task to write these rows and should own the widening migration; M2.1 deliberately did not add one, having no rows to write. |
| M2.1 | Nothing persists the manual-entry queue — it lives for the duration of one parse run. M2.3 owns the reconciliation queue and its table; until then an unparseable purpose string is visible only as a `ca.purpose.queued` log event. |
| M0.5 | Integration modules each create a scratch database whose name is a module constant, and the build runs several agents against one Postgres — one session's `DROP DATABASE ... WITH (FORCE)` then kills another mid-test, which reads as flakiness (observed once during this task). `tests/integration/test_status_api.py` and `test_scheduler.py` key the name by pid; `test_migrations.py`, `test_status_sync.py` and `test_backup_restore.py` do not. CASCADE` exercises the trigger (both are asserted in `tests/integration/test_journal.py`). Harmless today, but a schema change that drops that FK would silently narrow what the plain form proves. |
