## Box 3 — daily EOD job runs unattended 5 consecutive sessions incl. self-heal on one induced failure

**PASS — by SIMULATION (frozen clock + re-dated fixture bytes, no network).** Stated explicitly per
M1.14's spec, which permits "5 real sessions or … a documented simulated-clock run."

Evidence: `tests/integration/test_eod_pipeline.py::test_five_consecutive_sessions_run_unattended_with_one_self_heal`
passes (re-run in isolation, `1 passed in 4.41s`; full file `5 passed`). What the test actually does:

- Drives five consecutive sessions **2024-07-08 .. 2024-07-12** through the *same* pipeline, one at
  a time, with **no human step** between runs.
- Time is an injected `FrozenClock(session)` per day (invariant #11 / B10) — **not** wall-clock,
  **not** five real calendar days.
- Bytes are **real UDiFF fixture bytes re-dated** to each synthetic session and served over an
  in-memory transport (`_consecutive_transport`); the suite ships two real dates and re-dates them
  to make five. **No network is touched.**
- The middle session (2024-07-10) is served a **500**, is left `FAILED(retryable)`, and raises a
  CRITICAL alert. The **next** day's run self-heals it via the lookback window while also publishing
  its own session — the recovery is by a later run's self-heal step, asserted not to be a human.
- End state asserted: all five sessions `PUBLISHED` in `sync_state` and non-empty in L1.

This is a faithful simulation of the unattended-loop-plus-self-heal behaviour the box demands, but
it is a simulation: five real consecutive live-network EOD sessions have **not** been run. The
production loop and its self-heal window are documented in `ops/runbooks/daily-eod.md` (lookback 7
days).

## Box 4 — archives downloadable

**PASS** (real bundle, checksums and L0 lineage verified end-to-end).

A real archive bundle exists for a backfilled date, `data/archives/2024-01-02/`
(`prices_raw.parquet`, `prices_raw.csv`, `manifest.json`). Independent verification:

- **Per-file checksums match.** `shasum -a 256` of each on-disk file equals the manifest's `sha256`
  (`prices_raw.parquet` → `50ad571f…`, `prices_raw.csv` → `972c676a…`).
- **Lineage maps every output to L0.** Both files' manifest lineage names L0 ref
  `cm02JAN2024bhav.csv.zip` (source `nse_bhavcopy_legacy`, sha256 `57b5654d…`). That L0 object
  physically exists at `data/L0/nse_bhavcopy_legacy/2024/01/cm02JAN2024bhav.csv.zip` and its
  computed sha256 is `57b5654d…` — matching both the manifest lineage **and** the
  `sync_state.checksum` for 2024-01-02 (PUBLISHED). Full L0→L1→bundle chain verified.
- **Live `GET /archives?date=2024-01-02`** returns the manifest with the same per-file hashes.
- **Download route verified in code + test.** `tests/integration/test_archives.py::test_files_download_and_verify`
  downloads every manifested file over `GET /archives/download` and asserts the bytes hash to the
  recorded sha256; the full file passes (`12 passed`).

**Operational caveat (not a code/data defect):** the *running* app container is a stale build — its
live OpenAPI exposes `/archives` (query) but **not** `/archives/download` (added by M1.12), so a
live `curl` of the download route 404s. The current source has the route and the integration test
exercises it green. A container restart/rebuild picks it up. Logged for ops; does not affect the
box, which is satisfied by the current codebase.
