## Box 2 — every fundamental datum carries (period_end, filing_date)

**PASS (structural; with a fixture caveat).**

`dataplatform/store/pit_fundamentals.py` declares the L1 schema with both fields **non-nullable**:

```
pa.field("period_end",  pa.date32(), nullable=False),
pa.field("filing_date", pa.date32(), nullable=False),
```

so a datum missing either cannot be written. `tests/unit/test_xbrl.py` proves it end-to-end on
parsed filings:

- `test` iterating every parsed fact asserts `isinstance(fact.period_end, date)` and
  `isinstance(fact.filing_date, date)` (lines 141–142).
- `period_end` comes from the document's own reporting-period element; `filing_date` from the
  index's dissemination timestamp — the two are independent: `fact.filing_date != fact.period_end`
  (line 161), and `tcs.filing_date > tcs.period_end` (line 172).
- A filing dated on or before its period is **rejected** (line 175), guarding invariant #7.
- A later filing restating an earlier period is stored as a **new record keyed by filing_date /
  filing_id**, both versions coexisting (M7.3 acceptance 3; store docstring + `read_pit`/`read_latest`).

PIT partitioning is by `filing_date`, making "what did we know then" a partition choice rather than
a `WHERE` clause a caller could forget — invariant #7 made structural.

**Caveat — test fixtures are hand-authored.** `tests/fixtures/xbrl/filing_v1/*.xml` carry the header
"Values are illustrative, not a real filing" (a Kaynes Q4 FY26 standalone filing plus its
restatement, in the real in-bse-fin 2020-03-31 taxonomy shape). The **real-fetch** evidence — an
actual NSE XBRL document, 19,935 B, sha256 `896516…5b84e` — lives in the Source Register, not in
the parsed test corpus. The parser is therefore exercised against taxonomy-accurate synthetic
documents, not the byte-for-byte fetched filing. Acceptable under B8 (frozen fixtures, offline
tests) and it does not weaken the (period_end, filing_date) guarantee, which is enforced by the L1
schema on any input; flagged for honesty.

> **RESOLVED 2026-09-03 (`ops/gates/M7-xbrl-rebuild.md`).** The caveat understated the problem. The
> synthetic documents were not taxonomy-accurate in the ways that mattered: they put one period per
> document (real filings carry a quarter *and* a cumulative column, usually sharing an
> `xbrli:period`), used an ISIN as the entity identifier (real ones use the NSE symbol and Ind-AS
> filings carry no ISIN), hung segments off `xbrli:segment` with a typed `SegmentName` member (real
> ones use `xbrli:scenario` with an explicit member on `ReportableSegmentsAxis` named by
> `DescriptionOfReportableSegment`), and used four element names — `TotalIncome`, `TotalExpenses`,
> `BasicEarningsPerShare`, `DilutedEarningsPerShare` — that appear in no real filing. Box 2's claim
> was true of the schema and remains true; what was untrue was the implied claim that the parser
> feeding it worked. `tests/fixtures/xbrl/` now holds 15 captured real filings and 2 captured index
> responses (`tests/fixtures/xbrl/README.md`), all of which parse.

> **General lesson for future GATE_AUDITs.** "Fixtures are synthetic but taxonomy-shaped" is not a
> caveat to note and pass on — it is the one condition under which a parser gate proves nothing
> about the parser. When a source row's status is VERIFIED from a real fetch but the parsed corpus
> is authored, the two pieces of evidence are about different artefacts, and the gap between them is
> exactly where a false-DONE lives. Ask for one real captured document in the corpus.

## Box 3 — backtest harness proves restated store is unreachable from PIT queries (structural unreachability proof)

**PASS.** This is the strongest-evidenced box and the one the audit acceptance singles out.

The quarantine (`dataplatform/query/quarantine.py`) is structural, not a runtime flag. A
`backtest_catalog()` opens its own DuckDB connection and registers **only** the PIT view; the
restated view and the sole `RestatedReader` capability are constructed **only** down the
`monitoring_catalog()` path (`_register_restated` is unreachable from a BACKTEST context). There is
no method on a backtest catalog that returns restated data and no argument that flips one on — "read
the restated store from a backtest" is a call with no receiver, not a guarded call that fails.

`tests/integration/test_quarantine.py` proves it from four independent angles, with the restated
data written to disk first so an empty reach is quarantine, not absence:

- `test_backtest_catalog_has_no_restated_view_but_has_pit` — `RESTATED_FUNDAMENTALS_VIEW not in
  backtest.views`, `PIT_FUNDAMENTALS_VIEW in backtest.views`.
- `test_restated_reader_capability_is_absent_from_a_backtest` — `backtest.restated()` raises
  `QuarantineError`.
- `test_deliberate_restated_read_from_a_backtest_raises` — `backtest.read_restated(ISIN)` raises
  (message: "monitoring-only").
- `test_backtest_sql_cannot_name_the_restated_view` — a hand-written
  `SELECT count(*) FROM "restated_fundamentals"` raises a DuckDB catalog error: the view is not
  registered on the backtest connection (the "separate catalog" guarantee at the SQL layer).
- `test_the_restated_data_exists_on_disk_so_the_empty_reach_is_quarantine` — control: the two
  restated RELIANCE rows ARE readable through `RestatedStore` directly, yet the backtest pointed at
  the same lake still raises.

Confirmed independently at the break-condition layer: `tests/unit/test_fundamental_bc.py`
acceptance 3 — a declining series written into the *restated* store with the PIT store flat yields
`INTACT`; the restated decline is invisible to `evaluate_segment_revenue_decline`, whose data comes
from `backtest_catalog` (no restated reader). Physical separation is also confirmed:
`RESTATED_ROOT_NAME = "RESTATED"` is a sibling root of the L1 layers that `paths.py` cannot form a
path under, and the PIT dataset lives under `data/L1/pit_fundamentals/`.

Monitoring symmetry (M7.2 acceptance 2) also holds: `monitoring_catalog()` registers both views,
reads restated figures back as `ProvenancedFundamental` stamped with the `RESTATED` store, and a T2
`EvidenceBundle` round-trips that provenance so the journal records which store each datum came from.
