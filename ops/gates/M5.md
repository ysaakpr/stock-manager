## Box 1 — The AI/Robotics case (₹10k/mo, 5 yr, high risk) created end-to-end through the interview

**PASS.** (Interview flow is deterministic; the theme map / theses it consumes are stub/fixture — see limitation.)

The case is *not* hand-built. `test_case_created_through_interview_flow_and_ratified` runs the §5.1
transcript from the B9 fixture through `conduct_interview` → `build_proposal`, which **derives** the
seven §5.2 policies from it; the derived policy set — not a hand-written one — is what is proposed.
The fixture's `expected_policies` block is a drift guard the test asserts equality against, so a
change in the recommendation tables fails loudly. Verified values match the §5.2 reference case:

| Policy | Derived from | Asserted value |
|---|---|---|
| rotation dial (tactical %) | risk_appetite = aggressive | 30 |
| max position % | concentration = medium | 15 |
| max sector % | concentration = medium | 35 |
| min holdings | concentration = medium | 8 |
| drawdown review % | aggressive | 25 |
| max order value (₹) | 12× SIP instalment | 120000 |
| T2 cadence | 5-yr horizon (< 10y) | MONTHLY |

Interview inputs verified in the fixture: `sip_amount: 10000`, `sip_day: 1`, `horizon: 5`,
`risk_appetite: aggressive` (the "high risk" of the gate line). The interview flow is a deterministic
mapping table (`analyst/interview/flow.py`), not an LLM judgement.

*Stub caveat:* the theme map and per-holding theses fed into `build_proposal` are the fixture's
values (`provider="stub"`), not the output of a live A3/A5 mapper or A4 thesis engine call. Those
engines exist and their own verifies pass (M5.5, M5.6 green above), but the end-to-end case-build in
the paper run consumes fixture data for them, not model output.

## Box 3 — Runs unattended in paper mode 10 consecutive sessions; journal complete for every day incl. heartbeats

**PASS.** `test_ten_sessions_run_with_a_journal_entry_for_every_day` drives ten `SchedulerRunner.run_once`
calls, advancing a `FrozenClock` one calendar day between runs (B10 — injected clock), sessions
2026-09-01 .. 2026-09-10 inclusive. Verified:

- `state.sessions == list(SESSIONS)` — ten consecutive sessions actually ran, in order, each
  `JobState.SUCCEEDED`.
- Every one of the ten trading dates carries ≥ 1 decision-journal entry (queried from real Postgres).
- Exactly **10 `HEARTBEAT`** entries — one per session — satisfying invariant #9 (a quiet day still
  journals the checks it performed): `assert heartbeats == len(SESSIONS)`.

*Caveat (recorded, not a failure):* "unattended" here is the scheduler's `run_once` invoked ten times
in a loop with the clock advanced explicitly, not a wall-clock cron firing over ten real days. This
is the deterministic, replayable form the plan intends (B10, §8.3.3). The data-red interlock is
forced green in the run via an always-green `GreenGate` so the loop's green-day path is exercised;
the red-day short-circuit (`SKIPPED_DATA_RED`, invariant #10) is proved separately and passes:
`uv run pytest tests/unit/test_t0.py -q` → 16 passed. The dead-session interlock (AUTH_REQUIRED,
M5.15) likewise passes: `uv run pytest tests/unit/test_auth_interlock.py -q` → 15 passed.
