**Slot.** 05:30 / 05:45 daily. The busy windows the contract names are all avoided: the evening jobs
19:15–21:50 (and the 21:45 paper session's 30-minute budget), `fundamentals_forward` 02:00–04:45 (its
own deadline; worst case off the hosts 05:45, which does not matter here — a dump is an MVCC snapshot
and holds no host lease), and Saturday 09:00–11:00. 05:30 is after every writer of the day, so the
dump holds the day's paper session, journal and overnight captures. Both jobs finish well before the
first-Sunday `bse_ca_sweep` at 06:00.

**Credentials.** The live DSN is `DATABASE_URL`; the drill's optional target is the `SecretStr`
`RESTORE_DRILL_DATABASE_URL`. The password reaches `pg_dump`/`pg_restore` as `PGPASSWORD` in the
child environment only, passed to `docker run -e PGPASSWORD` by name — never in an argv, a log line
or a sidecar (`test_the_dump_passes_the_password_by_environment_only` asserts all three; a failing
tool's stderr is redacted, `test_a_failed_dump_redacts_the_password_and_leaves_no_partial`).

**Retention.** Newest dump of each of the last 14 days that have one + newest of each of the last 8
ISO weeks; the newest is always kept; only files named `trading-<stamp>.dump` (+ sidecar) are ever
pruned. At today's ~11 MB a full set of 22 dumps is ~250 MB.

**Failure surfacing.** Both are ordinary registered jobs: a raise is a FAILED `job_run`, visible on
`GET /status/jobs` and paged by `failure_alerts` like any other job. The disk guard refuses a dump
that would leave less than twice the newest dump + 1 GiB free.

## Drill 3 — the scheduler refuses an unmigrated database

Against a scratch empty database `trading_m15_4_guard_demo` (created and dropped for this), never the
live one, and without touching the running scheduler unit:

```
$ DATABASE_URL=<scratch empty db> uv run python -m dataplatform.scheduler run
[error   ] scheduler.refused  reason='14 migration(s) not applied: 0001_init.sql, …, 0014_job_run_retry_pending.sql. Run `make migrate`, then restart the scheduler.'
scheduler: refusing to start: 14 migration(s) not applied: …
[critical] alert              body='14 migration(s) not applied: …'
exit=5
```

`RestartPreventExitStatus=5` keeps systemd from restarting into the same refusal; the heartbeat goes
stale and `/health` turns 503 within `SCHEDULER_HEARTBEAT_STALE_AFTER_SECONDS` (300 s). The live
database has 0001-0014 applied, which is every migration on `main` at 6b52405, so the restart after
this merge starts normally — **unless another PR in this wave adds a migration (0015-0017 are
reserved) and merges first: then `make migrate` must precede the restart.**

## L0

The manifest was seeded once by hand, so the nightly job starts incremental:

```
$ nice -n 15 ionice -c3 uv run python -m dataplatform.store.backup l0     # DATA_ROOT = the real lake
backup.l0_manifest             files=224294 hashed=224294 manifest=/home/ubuntu/backups/l0/MANIFEST.sha256
backup.l0_mirror_unconfigured  reason='BACKUP_L0_MIRROR is unset: L0 has a manifest but no second copy'
        Elapsed (wall clock) time: 18:05   (idle I/O class, load ~10 from a running backtest)

$ uv run python -m dataplatform.store.backup l0       # the nightly shape: nothing new since
L0 manifest /home/ubuntu/backups/l0/MANIFEST.sha256: 224294 files, 0 new
wall=13.68 s

$ cd /home/ubuntu/stock-manager/data && shuf -n 2000 ~/backups/l0/MANIFEST.sha256 | sha256sum -c --quiet
sample of 2000: all OK
```

| Measure | Value |
|---|---|
| L0 | 9.7 GB, 224,294 files |
| Manifest | `~/backups/l0/MANIFEST.sha256`, 30 MB, `sha256sum -c`-compatible from the lake root |
| First (full) pass | 18 min wall at `ionice -c3` |
| Incremental pass, nothing new | 13.7 s (directory walk) |

**No off-box or second-disk target exists.** This host has one disk (`/dev/root`, 193 GB, 116 GB free;
the lake 9.7 GB, 224,294 files) and no configured remote. `BACKUP_L0_MIRROR` is therefore unset and
`l0_backup` logs `backup.l0_mirror_unconfigured` every night — the manifest gives *detection*
(a missing recorded file fails the job; `l0_verify` re-hashes bytes weekly), not *recovery*. The same
holds for the Postgres dumps, which share the disk with the database: they protect against a bad
migration, a dropped table or a corrupted cluster, not against losing the volume. **Owner decision:**
choose a target (second EBS volume, S3 via a mounted path, or an rsync host), set `BACKUP_L0_MIRROR`,
and add the same copy for `~/backups/postgres/`.
