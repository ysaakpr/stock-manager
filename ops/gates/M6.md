## Why this gate task (M6.9) is PARKED, not DONE

counts **any task not in state DONE as a failure** — including M6.8, the `NEEDS_SECRET` live-model

command **cannot mechanically exit 0** while M6.8 is open, and `orch set M6.9 DONE` refuses on that
exit code. The StubLLM audit above is genuinely complete and passing; only the mechanical closure of
the milestone gate is blocked, on the very credential this report names as the open item.

This is not a box failure and M6.8 is not a defect — marking it FAILED would retry a
credential-blocked task that cannot heal. Per AGENTIC_CONTEXT §1, a task requiring a credential that
does not exist is a **PARKED** exit. The identical situation exists at **M1.14** (GATE M1), which is
also stuck PENDING because its in-scope `NEEDS_GO` task M1.13 is PARKED — so this is a systemic
gate-command limitation, not an M6-specific problem, and how to resolve it (accept human-reserved
tasks as open items in `cmd_gate`, vs. supply the credential) is an owner decision, filed in
`HUMAN_DECISIONS.md`. M6.9 is PARKED pending it; the StubLLM verdict stands regardless of which way
that decision goes.
