Nothing in the stack applies migrations. The app comes up against an empty database, `/health` cannot read
`scheduler_heartbeat`, answers `503 UNKNOWN` (correctly — it refuses to report on evidence it lacks), and the
container healthcheck consumes that 503 as a failure. `/status/sync` in the same window is worse than a 503:

```

HTTP 500
```

An anonymous 500 with no body. `/health` explains itself on an unmigrated database; nothing else on the
surface does.

### The recovery, and why it does not rescue the box

`make migrate` — a documented target — fixes it, in one second, and the container self-heals on its next
probe:

```
19:35:27  app=running/healthy  postgres=running/healthy  health_http=200
19:35:38  app=running/healthy  postgres=running/healthy  health_http=200
```

So the *task-level* criterion — "reaches healthy with no manual steps beyond documented make targets" — is
technically met by `make up && make migrate`, and `make migrate` is documented (CLAUDE.md §Toolchain, and the
Makefile's own comment). The *plan's* box is not. It says `docker compose up` → healthy, and
`docker compose up` does not produce healthy, now or ever. Three things make this a real defect rather than
a wording quibble:

1. **`ops/README.md` § "Running it" lists `up / logs / psql / down / backup / restore` and *not* `migrate`.**
   An operator following the ops README verbatim gets a permanently unhealthy app and no line anywhere
   telling them why.
2. **The failure mode is silent-until-fatal.** A deployment that comes up unhealthy on first boot and needs
   an undocumented out-of-band step is a first-boot outage.
3. **It is already known.** `ops/BACKLOG.md` carries it: *"M0.4 | Nothing applies migrations on container
   start: a fresh `make up` leaves the app talking to an unmigrated DB until someone runs `make migrate`. An
   entrypoint step (or a `/health` degradation when `schema_migrations` is behind the files on disk) would
   make the gap visible instead of latent — belongs with whatever owns the app entrypoint."* The gate is
   where a known latent gap stops being deferrable.

### Second finding on the same surface — `make up` serves a stale image

Before the teardown, the running stack had been up ~1 hour and was **serving the M0.3-era image**, built
before M0.5 landed:

```
$ curl -s -w " HTTP %{http_code}" "localhost:8000/status/sync?date=2026-08-07"
```

the trading interlock (invariant #10) reads before it trades. Recorded here because it lives on the same
compose/entrypoint surface as the primary failure.

Three states distinguished on real evidence — `OK`, `STALE`, `NEVER_RAN`, plus `UNKNOWN` when the row cannot
be read (seen for real in box 1). The status code and the body agree in every case.

### Caveats — read these before treating the box as green

- **The stale path was forced by hand, not observed.** `age_seconds=3600` came from a `UPDATE ... beat_at`,
  because nothing in the stack keeps a scheduler beating (below). The *logic* is verified; the *situation* has
  never occurred here.
- **No scheduler runs in the deployed stack.** `docker compose ps --services` → `app`, `postgres`. The app's
  command is `uvicorn dataplatform.status.api:app`; `python -m dataplatform.scheduler run` is hand-started.
  In the stack as shipped, `/health` would report `NEVER_RAN` and 200 forever — the heartbeat check is
  live code over a signal nothing produces. Already in `ops/BACKLOG.md` (M0.6 row: *"Nothing runs the
  scheduler … the service belongs beside `app`"*), scheduled for M1.11.
- **`eod_pipeline` is a declared no-op** — it logs `note='no-op until M1.11 wires the ingestion pipeline'`.
  The heartbeat above is real; the work behind it is a placeholder, by design at M0.
- **The database is empty of market data.** `sync_state` held 0 rows before the audit's probe row. "Empty
  returns real state" is exactly what the box asks, but no endpoint on this surface has yet been exercised
  against a real ingestion.
- **Before migration, `/status/sync` returns a bare `500 Internal Server Error`** (box 1). Only `/health`
  degrades gracefully on an unmigrated database.

**Verdict: PASS**, on the migrated stack, with the caveats above.

### Caveats

- **Nothing leaves this host.** L0 is fingerprinted, never copied; no backup is uploaded anywhere. A disk
  failure loses the lake and every backup of it. Documented as a gap, and closing it needs a spending
  decision (§3.9) — correct to park, but the M0 gate should not be read as "backups exist" in the
  disaster-recovery sense. They exist on the same disk as the thing they protect.
- **Nothing schedules `make backup`, and nothing prunes `ops/backups/`.** Hand-run only, per the runbook.
- **`data/evidence/` is outside the backup manifest** (`ops/BACKLOG.md`, M5.1 row): the Postgres dump keeps
  the journal's references and loses what they refer to, so a restored journal is not reconstructable. An
  M5-era gap, not an M0 one, but it is the largest hole in what "restore" currently means.
- **The row counts are small.** 4 rows live, 3 seeded, 17 tables. 1.67 s is fixed overhead, not a projection
  for a ten-year L0 (~10⁵ files); the manifest re-hash is the part that grows.

**Verdict: PASS.**

the retry carries its history.

## Blast radius of this audit

`docker compose down -v` destroyed the `pgdata` volume while five other tasks were in flight. Nothing was
lost: the backup taken at 19:30, before the teardown, records the whole database as **5 rows** —
`job_run 1`, `scheduler_heartbeat 1`, `schema_migrations 3`, every other table zero
(`ops/backups/20260808T193031/`). No product data existed to lose. `DATA_ROOT` is a bind mount and was never
in scope: `find data/L0 -type f | wc -l` → 10, before and after.

The stack is left **up, migrated and healthy**, on an image built from current source — strictly better than
it was found, since the pre-audit stack was serving the stale pre-M0.5 image of finding 2. Scratch databases
created by the drills (`trading_m08drill`, `trading_m08drill_restore`) were dropped; `restore.sh` drops its
own.
